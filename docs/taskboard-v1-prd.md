# Codex Taskboard V1 产品需求文档

状态：V1 五个盒子已实现并通过全量自动验证，当前本地版本已加载；待 Snow 用下一项真实任务完成一次自然验收  
更新时间：2026-09-03  
产品负责人：Snow  
开发与验证：Codex Agent

## 1. 产品目标

Taskboard V1 是 Snow 管理 Codex 工作的全局任务控制台。

Snow 打开面板时，应当立即知道：

- 当前有哪些任务正在推进；
- 每个任务要达成什么目标；
- 目前做到哪个业务阶段；
- 最近完成了什么、下一步做什么；
- 哪些任务遇到阻碍，以及需要 Snow 补充什么；
- 哪些结果正在等待 Snow 最终确认。

Snow 的常规操作只保留四类：

1. 创建任务；
2. 补充评论或附件；
3. 必要时调整项目和优先级；
4. 最终确认。

项目归属建议、会话创建与关联、执行续跑、状态流转和阻碍恢复，应尽量由系统完成。

## 2. 产品模型

V1 保持简单的三层模型：

项目 → 任务 → 主执行会话

- 一个项目对应一个 Codex 本地项目和代码目录。
- 一个任务是 Taskboard 的管理对象。
- 一张活跃任务卡只有一个主执行会话。
- 其他历史会话只作为相关上下文，不参与当前状态控制。
- 全局是所有项目任务的汇总和创建入口，不是一个真实代码项目。

跨多个仓库的 Program 概念不在 V1 实现。

## 3. V0 基线与 V1 要解决的问题

V0 已具备项目、任务、会话、评论、附件、状态列和项目内自动认领；也已经验证过项目内未绑定任务可以创建执行会话并进入处理中。

V1 需要解决：

- 看板状态与会话实际执行状态不一致；
- 已有关联会话的任务需要 Snow 人工维护状态；
- 卡片评论和会话消息没有稳定汇入同一个执行入口；
- 阻碍任务补充材料后不能自动唤醒原会话；
- 自动扫描可能产生重复会话；
- 自动会话名称暴露内部提示词，无法肉眼识别；
- 全局创建任务时不能顺手确定项目并进入执行流程；
- 全局尚不能安全地限制并发和代码目录冲突。

## 4. 目标使用流程

### 4.1 创建

1. Snow 在全局或具体项目中创建任务。
2. 全局创建时，系统根据标题、描述、附件和项目历史自动推荐项目。
3. 创建界面显示项目下拉框，默认使用推荐结果；Snow 可以纠正。
4. 已有足够目标和材料的任务进入待认领。
5. 缺少项目、目标或必要材料的任务进入待立项，不参与自动认领。

### 4.2 认领和执行

1. 调度器从待认领中选择任务。
2. 没有主执行会话时，系统只创建一个新会话并绑定。
3. 新会话成功启动后，任务自动进入处理中。
4. Agent 根据任务描述、最新评论、附件和可自行查找的项目上下文执行。
5. Agent 持续回写当前阶段、最近完成和下一步。

### 4.3 阻碍与恢复

1. 材料、权限或业务决定不足时，Agent 将任务转为遇到阻碍。
2. 卡片必须明确显示缺少什么，以及 Snow 需要做什么。
3. Snow 在卡片补充评论或附件后，系统自动唤醒原主执行会话。
4. Agent 读取新增材料并判断阻碍是否解除。
5. 已解除则自动回到处理中；未解除则继续停在遇到阻碍并更新缺失项。

Snow 不需要回到会话重复提醒，也不需要手动修改状态。

### 4.4 交付、返工和完成

1. Agent 提交可验收结果后，任务自动进入等你确认。
2. Snow 在任务卡或主执行会话提出修改意见，两处效果相同。
3. 系统唤醒同一主执行会话，任务自动回到处理中。
4. Snow 验收通过后点击完成。

只有 Snow 的最终确认会把任务标记为完成。

## 5. 状态合同

| 状态 | 业务含义 | 自动行为 |
| --- | --- | --- |
| 待立项 | 尚不具备执行条件 | 不认领，显示缺少内容 |
| 待认领 | 信息足够，可以开始 | 进入调度队列 |
| 处理中 | 主执行会话正在推进 | 展示阶段、最近完成和下一步 |
| 遇到阻碍 | 需要 Snow 的材料、权限或决定 | 显示明确缺失项，等待新增输入 |
| 等你确认 | Agent 已提交可验收结果 | 等待 Snow 通过或返工 |
| 完成 | Snow 已确认结果可用 | 停止执行，保留记录 |

正常工作流不要求 Snow 手工移动状态。手工状态修改只保留为纠错和管理入口。

会话暂时空闲不等于任务完成；系统不能只凭会话停止就猜测等你确认或完成。

Taskboard 入口暂时离线也不等于业务任务必须停止。尚未完成认领或无法确认绑定的会话必须停；已经成功绑定的主执行会话可以在原任务范围内继续，并明确标记看板同步延后，待入口恢复后补写评论和状态。

## 6. 主执行会话合同

### 6.1 唯一性

- 一张活跃任务卡只有一个主执行会话。
- 定时检查、页面刷新和重复事件不得创建第二个执行会话。
- 已有主执行会话时，系统必须继续或唤醒原会话。
- 相关历史会话可以被 Agent 只读查看，但不成为新的状态控制者。

### 6.2 可读名称

自动创建的 Codex 会话名称采用：

Taskboard · {任务标题}

示例：

Taskboard · 西安流水核对

要求：

- Codex 侧栏和任务详情中的主执行会话名称一致；
- 名称不包含技能名、任务 ID、项目 ID、XML 标签或内部执行提示词；
- 任务 ID、项目 ID 和执行指令保留在元数据及提示正文中；
- 活跃任务改名时同步主执行会话名称；
- 服务启动时回填仍由 Taskboard 自动命名的历史主执行会话，避免遗留“新聊天”；
- Snow 自定义会话名称后，只关闭自动跟随任务标题，不解除主执行会话身份和唯一性；
- 同名任务必须区分时，仅追加简短序号，例如（2）；
- V1 保证新会话正确命名，不批量重命名全部历史会话。

当前源码只设置了 Taskboard 数据库中的短标题，但原生 Codex 侧栏会根据首次提示词生成标题。实现时必须在原生 Codex 会话创建成功后同步改名，不能只改 Taskboard 内部字段。

## 7. 任务卡信息

V1 暂不展示完成百分比。任务卡和详情页应清楚表达：

- 标题；
- 所属项目；
- 目标；
- 当前阶段；
- 最近完成；
- 下一步；
- 阻碍及所需输入；
- 优先级；
- 截止日期；
- 主执行会话；
- 最后活动时间。

卡片首页优先显示当前阶段和下一步；完整过程保留在详情和会话中。

## 8. 调度规则

待认领任务按以下顺序选择：

1. 已逾期或今天到期；
2. 截止日期更近；
3. 优先级更高；
4. 创建时间更早。

最终目标是全局最多同时推进 3 张任务卡：

- 不存在代码目录冲突的任务可以并行；
- 相同工作目录或存在明确改码冲突的任务排队；
- 阻碍中和等你确认不占执行并发，但仍保留主执行会话；
- 生产写入、部署、资金、权限和对外发送继续遵守单独确认边界。

## 9. 开发周期与交付盒子

开发采用五个盒子。每个盒子完成后都使用真实路径验收；未通过时只修当前盒子，不提前扩展后续范围。

当前实现状态：五个盒子的代码与自动验证均已完成。由于 Snow 后续明确要求不得新建或 fork 协调、实现、审查线程，剩余验收统一放在现有主线程和下一项真实任务中完成，不再为每个盒子制造独立测试任务或额外会话。

### 盒子 1：一张卡、一个可识别会话

预计：0.5—1 个有效开发日

范围：

- 固化主执行会话唯一性；
- 自动会话名称改为 Taskboard · 任务标题；
- 新会话创建后同步原生 Codex 侧栏标题；
- 修复重复扫描产生重复会话的直接路径。

验收：

- Finance 新任务只产生一个主执行会话；
- 侧栏名称可直接识别；
- 刷新和再次扫描不新增会话；
- 自动进入处理中。

### 盒子 2：状态和进度自动同步

预计：1—1.5 个有效开发日

范围：

- 执行开始自动进入处理中；
- Agent 提交结果自动进入等你确认；
- Snow 返工后自动回到处理中；
- 卡片展示目标、当前阶段、最近完成和下一步；
- 不用空闲状态猜测完成。

验收：

- Snow 不手工移动状态，也能看见真实进度；
- Finance 任务完整走完待认领、处理中、等你确认、返工、处理中。

### 盒子 3：评论、附件和阻碍恢复

预计：1—1.5 个有效开发日

范围：

- 卡片评论与主执行会话消息汇入同一执行通道；
- 卡片新增附件自动投递给主执行会话；
- 材料不足自动进入遇到阻碍并展示缺失项；
- 新材料到达后自动唤醒原会话并判断是否解除阻碍。

验收：

- 用缺少一份流水的 Finance 任务制造真实阻碍；
- Snow 只在卡片补附件；
- 原会话自动恢复，没有第二个会话，卡片自动回到处理中。

盒子 1—3 完成后，项目内流程达到首个可日常使用版本。

### 盒子 4：全局创建与项目推荐

预计：1—1.5 个有效开发日

范围：

- 全局视图直接创建任务；
- 根据内容自动推荐项目；
- 提供项目下拉框供 Snow 修正；
- 未确定项目时保存为待立项；
- 确定项目后进入对应项目的待认领队列。

验收：

- Snow 不离开全局页面即可创建 Finance 任务；
- 推荐正确时零额外操作，推荐错误时只改一次下拉框；
- 卡片在全局和目标项目中显示一致。

### 盒子 5：全局调度、并发和整体收口

预计：1—1.5 个有效开发日

范围：

- 全局调度按日期、优先级和创建时间排序；
- 最多并行 3 个任务；
- 同工作目录冲突时排队；
- 全局面板明确显示正在推进、等待 Snow 和遇到阻碍的任务；
- 完成首轮使用说明和统筹线程交接。

验收：

- 创建多张低风险测试卡，证明并发上限和冲突排队；
- 不出现重复会话或错误抢占；
- Snow 仅查看全局即可判断当前工作面。

## 10. 周期预估

- 首个可日常使用版本：盒子 1—3，约 3—4 个有效开发日。
- 完整 V1：盒子 1—5，约 5—7 个有效开发日。
- 日历周期建议预留 1—2 周，包含 Snow 的真实任务验收、反馈和一次回归修正。

这里的一个有效开发日是可以连续进行实现与验证的工作量，不要求 Snow 全天配合。Snow 通常只需要在每个盒子的真实验收节点使用一次功能并反馈结果。

若原生 Codex 不提供稳定的会话改名或唤醒接口，当前盒子停止并提交证据与最小替代方案，不把该风险静默扩散到后续盒子。

## 11. V1 验收标准

- Snow 不需要为了正常推进任务手工维护状态。
- 看板状态和主执行会话的实际状态一致。
- 一张任务不会因定时扫描、刷新或追加意见产生多个执行会话。
- 卡片评论、附件和会话消息都能唤醒同一主执行会话。
- 遇到阻碍时，卡片明确显示 Snow 需要补充什么。
- 自动创建的会话在 Codex 侧栏可以直接识别。
- 全局创建可以自动推荐项目并允许下拉修正。
- 全局最多并行 3 个任务，冲突任务不会同时占用同一工作目录。
- Snow 只看全局面板就能判断正在推进的任务、下一步和需要自己处理的事项。

## 12. V1 不做

- Program 或跨多个仓库的上层项目模型；
- 全量整理、关联或重命名历史会话；
- 完成百分比；
- 自动拆分所有子任务和复杂依赖图；
- 无人确认的生产部署、真实数据写入、资金操作、权限变更或对外发送。

## 13. 已确认的产品决策

- 第一痛点是看清手头有哪些任务、当前进度和目标。
- 新任务采用一任务一主执行会话。
- Snow 只承担创建、补材料、调整优先级和最终确认。
- 材料不足进入遇到阻碍，并明确显示缺失内容。
- 卡片评论和会话消息效果等价，统一唤醒原执行会话。
- 暂不使用完成百分比。
- 暂不整理全部历史会话。
- 全局创建采用自动推荐项目加下拉修正。
- 调度按日期、优先级和创建时间，安全任务可以并行。
- 全局并发上限为 3。
- 自动会话名称采用 Taskboard · 任务标题。
- 每个盒子由 Luna Max 实现，并由 Sol Medium 独立审查；当前盒子通过后再进入下一盒。
- 上述模型分工后来被“只使用现有主线程、禁止新建或 fork 线程”的指令覆盖；实现与自动验证在当前主线程内完成，最终以 Snow 的自然任务验收为准。
